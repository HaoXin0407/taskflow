# TaskFlow 项目分步搭建教程

> 面向人群：Java 后端 / 全栈求职者，用 IntelliJ IDEA 2025.3.3 + MySQL 8 + VS Code 搭建
> 目标：从零跑通一个能写进简历、经得住面试追问的全栈项目

---

## 一、开始之前：先想清楚你要的是什么

网上大量教程教你做「学生管理系统」「图书管理系统」，问题在于：

- 面试官一眼看出是练手项目，没有业务深度
- 追问「你这个项目的亮点是什么」，只能答"用了 Spring Boot"
- 简历上写完，面试官不感兴趣

**本项目的选题思路**：不选业务简单的 CRUD，而选一个**有完整业务闭环**的系统。

工单系统天然具备三个可讲的深度点：

| 深度点 | 为什么能讲 |
|--------|-----------|
| **状态机** | 6 个状态 + 7 个动作，非法流转必须拦截，这是真实的工程问题 |
| **多级串行审批** | 审批链数据化而不是写死 if-else，可扩展性好 |
| **RBAC 权限体系** | 前端菜单动态渲染 + 后端接口鉴权，前后端双重校验 |

难度控制：技术栈都是主流中间件，没有 Redis / 消息队列 / 微服务，避免劝退；
但每个模块都有可以深挖的设计点，这是「适中难度 + 高含金量」的平衡点。

## 二、环境准备清单

在写第一行代码前，先确认你的电脑能跑起来。

### 2.1 需要安装的东西

| 软件 | 版本要求 | 检查命令 |
|------|---------|---------|
| JDK | **17 或 21**（不要用 8，也不要用 25） | `java -version` |
| Maven | IDEA 自带即可，但需把 Maven home path 改为 `Bundled (Maven 3)` | `mvn -v` |
| MySQL | 8.0 | `mysql --version` |
| Node.js | 18+ | `node -v` |
| IDEA | 2025.3.3 | — |
| VS Code | 最新版 | — |

### 2.2 JDK 配置：IDEA 里必须改 4 处 ⚠️

**Spring Boot 3.x 要求 JDK 17 及以上。** 装好后，IDEA 里**四处都要改**，只改一处会继续报错：

| # | 位置 | 改什么 |
|---|------|--------|
| 1 | `File → Project Structure → Project` | SDK 选 JDK 17，Language level 选 **17** |
| 2 | `Settings → Build Tools → Maven → Runner` | JRE 选 **Project JDK (17)** ← 最容易漏 |
| 3 | `Settings → Build Tools → Maven` | Maven home path 改成 **Bundled (Maven 3)** ← 解决 Guice 报错 |
| 4 | `Settings → Build Tools → Maven → Importing` | JDK for importer 选 **17** |

**第 3 处为什么必须改**：IDEA 默认选 `Use Maven Wrapper`，会去连外部 Maven 3.9.x，
而 IDEA 内置的 maven3-server 期望 3.10.x 的组件布局，两者不兼容，报：

```
[Guice/MissingImplementation]: No implementation for ArtifactHandlerManager was bound
```

这是 IDEA 2025.x 的已知兼容问题，与你的代码无关。

> 更详细的图文步骤见 [环境配置指引.md](环境配置指引.md)

### 2.3 修改系统 JAVA_HOME（推荐）

IDEA 内置配置只影响 IDE，命令行用 JDK 25。

管理员 PowerShell 执行：

```powershell
[Environment]::SetEnvironmentVariable("JAVA_HOME", "C:\Program Files\Java\jdk-17.0.20.1", "Machine")
$mp = [Environment]::GetEnvironmentVariable("Path", "Machine")
[Environment]::SetEnvironmentVariable("Path", "$mp;%JAVA_HOME%\bin", "Machine")
```

执行后必须重开终端，用 `java -version` 确认显示 17。

## 三、第一步：导入数据库（10 分钟）

### 3.1 启动 MySQL 服务

Windows 上打开 PowerShell（管理员）：

```powershell
net start mysql80
```

> 服务名可能是 `mysql80` 或 `mysql`，用 `sc query | findstr mysql` 查看。

### 3.2 执行建库脚本

**方式 A：用命令行客户端（推荐，最快）**

新建一个 `init.sql.txt`，把 `sql/taskflow.sql` 内容粘进去，保存时编码选 UTF-8，
然后在 MySQL Command Line Client 里：

```sql
SOURCE C:/Users/你的用户名/path/to/taskflow.sql;
```

**方式 B：拖拽文件**

打开命令行客户端，输入 `SOURCE ` 然后把 `taskflow.sql` 文件拖进窗口，回车。

**方式 C：命令行重定向**

```bash
mysql -uroot -p < taskflow.sql
```

### 3.3 验证

```sql
USE taskflow;
SHOW TABLES;              -- 应该看到 12 张表
SELECT * FROM sys_user;   -- 应该有 5 个用户
```

如果这步失败，后面全都会失败，务必先确认。

## 四、第二步：创建后端工程并导入 IDEA

### 4.1 在 IDEA 里创建 Maven 项目

```
File → New → Project
  Name: taskflow-backend
  Language: Java
  Build system: Maven
  JDK: 17
```

创建后，把本项目 `backend/` 目录下的文件复制进去，覆盖掉自动生成的 `src` 目录。

或者更简单：直接把 `backend` 整个文件夹拖到 IDEA 里，用「Open」打开，
IDEA 会自动识别为 Maven 项目并下载依赖。

### 4.2 配置 Maven

如果你的 Maven 依赖下载慢，配置国内镜像：

在 `C:\Users\你的用户名\.m2\settings.xml` 中添加：

```xml
<settings>
  <mirrors>
    <mirror>
      <id>aliyun</id>
      <mirrorOf>central</mirrorOf>
      <name>阿里云公共仓库</name>
      <url>https://maven.aliyun.com/repository/public</url>
    </mirror>
  </mirrors>
</settings>
```

### 4.3 改数据库密码 ⚠️

打开 `src/main/resources/application.yml`，把密码改成你自己的：

```yaml
spring:
  datasource:
    password: '你的MySQL密码'
```

### 4.4 启动

右键 `TaskFlowApplication.java` → Run。

看到这段输出就成功了：

```
====================================================
  TaskFlow 后端启动成功！
  接口地址: http://localhost:8080/api
  接口文档: http://localhost:8080/api/doc.html
====================================================
```

日志里还会出现：

```
已将 5 个用户的明文密码升级为 BCrypt 密文
```

## 五、第三步：创建前端工程（VS Code）

### 5.1 终端执行

```bash
cd taskflow/frontend
npm install
npm run dev
```

浏览器会自动打开 `http://localhost:5173`

### 5.2 登录

| 账号 | 密码 | 能看到什么 |
|------|------|-----------|
| `admin` | 123456 | 全部功能（含系统管理菜单） |
| `manager` | 123456 | 工单受理、审批中心 |
| `zhangsan` | 123456 | 只能看/创建自己的工单 |

**强烈建议三个账号都登一遍，体会权限差异** —— 面试时讲权限体系，这是最直观的演示。

### 5.3 跨域为什么不用管

`vite.config.js` 里配了代理：

```js
proxy: {
  '/api': { target: 'http://localhost:8080', changeOrigin: true }
}
```

前端代码里只用 `/api/xxx` 相对路径，Vite 帮你转发到后端，不存在跨域。
后端的 CORS 配置是双保险（生产环境前后端不同域时需要它）。

## 七、面试时怎么讲（30 秒电梯版）

> "我做的是一个企业级工单流转与审批协同平台，前后端分离。
> 技术栈是 Spring Boot 3 + MyBatis-Plus + MySQL 8 + Vue3。
>
> 核心是工单**状态机**：6 个状态、7 个流转动作，我把状态和允许动作的映射
> 集中定义在枚举里，Service 层统一校验，非法流转在入口就被拦掉，
> 同时每次流转都写一条轨迹记录，保证全链路可追溯。
>
> 权限用 RBAC，前端根据后端返回的权限标识动态渲染菜单和按钮，
> 后端用 `@PreAuthorize` 再校验一次，两边都拦才算安全。
>
> 还有多级串行审批，审批链是存在节点表里的，加一级审批不用改代码。"

这段话包含了：**业务抽象能力、状态机设计、权限设计、可扩展性**四个考察点。

## 八、常见问题排查

### 启动就报错

**① `Communications link failure` / 连不上数据库**

```bash
# 检查 MySQL 服务是否启动
net start mysql80
# 检查 application.yml 里的账号密码
# 检查数据库名是否创建了 taskflow
```

**② `Access denied for user 'root'`**

密码错了，或者 MySQL 用了 caching_sha2_password 而老驱动不支持。
本项目用的是 `mysql-connector-j`（新版），一般不会遇到。

**③ `Unknown database 'taskflow'`**

SQL 脚本没执行成功，回去看第三节。

**④ `Public Key Retrieval is not allowed`**

`application.yml` 的 url 里必须带 `allowPublicKeyRetrieval=true`，本项目已经配好了。

**⑤ `[Guice/MissingImplementation]: No implementation for ArtifactHandlerManager was bound`**

IDEA 2025.x + `Use Maven Wrapper` 的已知兼容问题，与代码无关。
改成 `Settings → Build Tools → Maven → Maven home path` = **Bundled (Maven 3)**，
然后点 🔄 Reload All Maven Projects。详见 [环境配置指引.md](环境配置指引.md)。

**⑥ `Could not find artifact xxx in aliyun`**

镜像没加错，是**依赖的 artifactId 写错了**。本项目踩过一次：

```
❌ 错误：com.github.xiaoymin:knife4j-openapi3-jakarta
✅ 正确：com.github.xiaoymin:knife4j-openapi3-jakarta-spring-boot-starter
```

Spring Boot 3 需要用带 `-spring-boot-starter` 后缀的 jakarta 版本，且版本 ≥ 4.4.0。
本项目 pom 里已加注释说明。

**如何确认某个依赖到底存不存在**（不用猜）：

```bash
# 返回 200 = 存在，404 = 不存在
curl -sL -o /dev/null -w "%{http_code}\n" \
  "https://repo1.maven.org/maven2/com/github/xiaoymin/knife4j-openapi3-jakarta-spring-boot-starter/4.5.0/knife4j-openapi3-jakarta-spring-boot-starter-4.5.0.pom"
```

查全部可用版本：

```bash
curl -s "https://repo1.maven.org/maven2/组路径/构件名/maven-metadata.xml"
```

**⑦ `Web server failed to start. Port 8080 was already in use`**

端口被占（本项目 Tomcat 随机端口被占说明你启了两个实例，或 IDEA 里 Run 没停干净）：

```bash
netstat -ano | findstr :8080
taskkill /PID <进程号> /F
```

或者改 `application.yml` 里的 `server.port`。

## 二 · 启动期踩过的真实坑（面试可讲）

下面这几个都是启动时真实报错并已修复，记录下来避免重复踩。

### 坑 1：Bean 循环依赖导致启动直接失败

**报错**：
```
Error creating bean with name 'jwtAuthenticationFilter':
Requested bean is currently in creation:
Is there an unresolvable circular reference?
```

**依赖环**：
```
jwtAuthenticationFilter → authService → passwordEncoder（在 SecurityConfig 里）
                                                              ↓
        securityConfig ←──────────────────────────────────────┘
```

**根因**：`PasswordEncoder` 定义在 `SecurityConfig` 中，
而 `SecurityConfig` 又注入了 `JwtAuthenticationFilter`，后者依赖 `AuthService`，
`AuthService` 依赖 `PasswordEncoder` —— 构成闭环。Spring Boot 2.6+ 默认禁止循环依赖。

**解法**：把与"认证算法"相关的 Bean 抽到独立配置类 `PasswordConfig`，
**配置类职责越单一，被其他 Bean 依赖的副作用就越少**。

**加保险**：给 `JwtAuthenticationFilter` 的 `AuthService` 依赖加 `@Lazy`，
让Spring 注入代理对象而非真实实例，即使将来依赖链变化也不会死锁。

### 坑 2：`@Value` 注入 Map 失败

**报错**：
```
Could not resolve placeholder 'taskflow.ticket.sla-hours'
```

**根因**：application.yml 里 `sla-hours` 是嵌套结构：
```yaml
sla-hours:
  1: 24
  2: 72      # 下面还有子键
```
而 `@Value` **只能解析单个标量值**，遇到嵌套结构就无从下手。

**解法**：改用 Spring Boot 3 推荐的 `@ConfigurationProperties`，
把它绑定到强类型类 `TicketProperties` 上。

**面试怎么讲**：`@Value` 适合简单值注入，但有三大硬伤 ——
无法绑定复杂结构、key 写错编译期发现不了、配置与代码强耦合。
`@ConfigurationProperties` 类型安全 + 支持嵌套 + IDE 有补全。

### 坑 3：编译期"未报告的异常"

**报错**：
```
java: 未报告的异常错误java.security.NoSuchAlgorithmException;
必须对其进行捕获或声明以便抛出
```

**根因**：`MessageDigest.getInstance()` 和
`ObjectMapper.writeValueAsString()` 声明的是**受检异常**
（编译期就要求处理），而我习惯性当成了免检异常。

**涉及文件**：`JwtUtils`、`OperLogAspect`。

**记住**：Java 里抛受检异常的方法（`getInstance`、`read`、`write`
等）必须 try-catch 或 `throws`，否则编译不过。

### 坑 4：IDEA 启动报 `Could not resolve placeholder 'taskflow.jwt.secret'`

**这个报错有个隐蔽之处**：application.yml 明明在 `src/main/resources` 里，
但 IDEA 用的是**内置编译器**而不是 Maven，导致资源文件没被复制到 `target/classes`，
配置文件根本没被加载。

**怎么一眼看穿**：对比启动日志里 Tomcat 的上下文路径：

```
正常：[Tomcat].[localhost].[/api]     ← yml 加载成功
异常：[Tomcat].[localhost].[/]         ← yml 压根没加载
```

**解决（推荐）**：让 IDEA 委托给 Maven 构建

```
Settings → Build, Execution, Deployment → Build Tools → Maven → Runner
  ☑ Delegate IDE build/run actions to Maven
```

这样每次编译都会由 Maven 执行，资源文件自动复制到 `target/classes`，
行为和命令行 `mvn clean package` 完全一致，不会再有这种玄学问题。

**顺带检查三个常见干扰项**：

```
① src/main/resources/ 下有多个配置文件？
   application.properties 优先级高于 application.yml，两者共存容易互相覆盖。
   → 只保留 application.yml

② 有 Spring Initializr 生成的残留启动类？
   比如 com/itheima/xxx/Application.java 和 com/taskflow/TaskFlowApplication 并存，
   两个 @SpringBootApplication 会让 Spring Boot 启动类检测冲突。
   → 删掉用不到的

③ target/classes 里没有资源文件？
   → 说明确实没复制，按上面配 Maven 委托
```

### 坑 5：Maven 编译报「找不到符号 getXxx()」几十个

**报错**：
```
[ERROR] .../DashboardService.java:[44,10] 找不到符号
[ERROR]   符号:   方法 setTotal(Long)
[ERROR]   位置: 类 com.taskflow.vo.DashboardVO$Summary
```

**根因**：Lombok 没生效。**三处配置必须配套**，缺一不可：

```xml
<properties>
    <lombok.version>1.18.42</lombok.version>   <!-- ① 版本必须 >= 1.18.42 -->
</properties>

<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <version>${lombok.version}</version>
    <scope>provided</scope>                    <!-- ② 不能用 optional + plugin exclude -->
</dependency>

<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <parameters>true</parameters>
        <encoding>UTF-8</encoding>
        <annotationProcessorPaths>              <!-- ③ JDK17+ 必须显式声明 -->
            <path>
                <groupId>org.projectlombok</groupId>
                <artifactId>lombok</artifactId>
                <version>${lombok.version}</version>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
```

**三个坑各自的原理**：

| 配置 | 缺了会怎样 | 为什么 |
|------|-----------|--------|
| ② provided scope | 编译期找不到注解处理器 | Lombok 是 **Annotation Processor**，编译期就要参与生成 getter。用 `optional` + `spring-boot-maven-plugin` 的 `<excludes>` 排除它，编译期就挂了 |
| ③ annotationProcessorPaths | 同样报「找不到符号」 | JDK 17+ / Maven 3.10 下，靠 classpath 自动发现注解处理器的机制会失效，必须显式声明路径 |
| ① 版本 ≥ 1.18.42 | `ExceptionInInitializerError: com.sun.tools.javac.code.TypeTag :: UNKNOWN` | 旧版 Lombok 访问 JDK 内部 API，被 JPMS 模块化系统拦截 |

**记住**：`provided` 作用域的含义是「编译期需要、打包时不包含」，
这正是 Lombok 想要的语义 —— 不需要额外 exclude。

### 依赖下载失败

IDEA 里 `File → Settings → Build Tools → Maven`：
- 勾选 `Work offline` 关掉
- 在 `settings.xml` 配阿里云镜像（见 4.2）

Maven 导入报红但其实下载完了：右键项目 → Maven → Reload Project。

### 前端问题

**① `npm install` 很慢**

```bash
npm config set registry https://registry.npmmirror.com
```

**② 页面白屏，控制台报路由错误**

检查 `main.js` 里是否引入了 `permission.js` 指令。如果没引入，`v-has-perm` 会报错。
本项目的做法是在 `main.js` 中统一注册。

**③ 接口 404 / 后端连不上**

确认后端已启动，且 `vite.config.js` 的代理地址与后端端口一致。

### 登录报「令牌无效」

- 检查数据库密码是否被改过
- 检查 `application.yml` 的 `taskflow.jwt.secret` 是否被改动（改了会导致旧 token 全部失效，重新登录即可）

## 九、下一步可以做的加分项

按性价比从高到低排序：

1. **单元测试**：给 `TicketService.handleAction` 写测试，覆盖各种状态流转的合法/非法场景
2. **Redis 缓存**：工单详情加缓存，用 `@Cacheable`，讲「缓存穿透/击穿/雪崩」
3. **导出 Excel**：工单列表导出，用 EasyExcel，讲大数据量导出要用的「流式写出」避免 OOM
4. **WebSocket 通知**：工单状态变更实时推送，比轮询更优雅
5. **Docker 部署**：写 Dockerfile + docker-compose.yml，一键部署

其中第 1 项最值得做，因为**面试官很爱问「你怎么保证你的状态机是对的」**，
有测试代码和没有测试代码，答案完全不一样。
### 坑 6：普通员工登录后左侧功能栏空白

**现象**：admin / manager 菜单正常，但 zhangsan、lisi、wangwu 登录后侧边栏空白，
只剩一个没有文字的蓝色高亮块。

**排查思路（按顺序，成本从低到高）**：

```
① 登录时接口返回了 permissions 吗？
   F12 → Network → /auth/login → 看响应体里 permissions 是不是空数组
   → 空数组说明是数据问题，不是前端问题

② 查数据库确认：
   SELECT r.role_code, p.perm_code
   FROM sys_role r
   LEFT JOIN sys_role_permission rp ON rp.role_id = r.id
   LEFT JOIN sys_permission p ON p.id = rp.permission_id
   ORDER BY r.id, p.id;
   → 如果某角色一条记录都没有，就是 sys_role_permission 表的问题
```

**本次的真实根因**：SQL 脚本里写角色权限时少了一列。

```sql
-- 错误写法（我写的，第 2 个值漏了 permission_id）
INSERT INTO `sys_role_permission` (`role_id`,`permission_id`) VALUES
(3,1),(2),(2,10),(2,11),(3,20),...;
--                     ^^^ 只有 1 列
```

MySQL 报 `Column count doesn't match value count`，
**整条 INSERT 全部不执行**，普通员工于是一个权限都没有。

**为什么难发现**：导入 SQL 时这个错误容易被忽略（后面还有很多成功执行的语句），
但它的影响是「整条失效」而不是「少一条」。

**修复：改用子查询写法，天然防错**

```sql
-- 按 perm_code 反查 id，不硬编码数字，不会再写错列数
INSERT INTO `sys_role_permission` (`role_id`,`permission_id`)
SELECT 3, id FROM `sys_permission`
WHERE perm_code IN (
  'dashboard','ticket','approval','notice',
  'ticket:list','ticket:add',
  'approval:list','approval:submit','notice:list'
);
```

好处：可读、不受权限 ID 变动影响、不会写错列数。

**用调试接口快速定位**：项目内置了排查工具

```
GET /api/debug/permission?username=zhangsan
GET /api/debug/permission          # 不传则输出所有用户
```

返回内容包括：该用户的角色、权限标识列表、菜单权限数，
以及**逐个模拟前端菜单过滤的结果**，直接告诉你每个菜单
「显示还是隐藏、为什么」：

```json
{
  "username": "zhangsan",
  "roles": ["USER"],
  "permissionCount": 9,
  "permissions": ["dashboard","ticket",...],
  "routeChecks": [
    { "route": "dashboard",     "menuVisible": true,  "reason": "无权限要求，所有登录用户可见" },
    { "route": "ticket/list",   "menuVisible": true,  "reason": "拥有权限 ticket:list" },
    { "route": "system/user",   "menuVisible": false, "reason": "缺少权限 system:user → 被过滤" }
  ]
}
```

如果 `permissions` 是空数组，会直接给出警告和 role_id 提示。

> ⚠️ 该接口在安全白名单里（免登录），生产环境请从 `WHITE_LIST`
> 中移除 `/debug/**`，或给类加 `@Profile("dev")`。

**还要注意**：前端权限缓存存在 localStorage。

否则 Pinia 里的旧权限还在，侧边栏依然空白。

### 坑 7：发起审批时审批人下拉框「无数据」+ 提示无访问权限

**现象**（截图表现）：
- 审批人下拉框点开显示「无数据」
- 强行点提交提示「无访问权限」
- 现象自相矛盾（既不能选人，又不能提交），功能完全卡死

**根因：一个接口承担了两种语义**

```
前端选择审批人时调用了 GET /system/user/list
                ↓
这个接口在 UserController 上，类级注解：
  @PreAuthorize("hasAuthority('system:user') or hasRole('ADMIN')")
                ↓
system:user 是「用户管理」模块的权限，只有管理员有
普通员工调用 → 403 → 下拉框无数据
```

而发起审批是**所有员工的日常操作**，却依赖了管理模块的接口，
于是形成死锁：不选人不能提交，选不了人也不能提交。

**修复：按使用场景拆分接口**

```java
// 新增 CommonController —— 业务场景，所有登录用户可用
@GetMapping("/common/users")
public Result<List<Map<String, Object>>> users() {
    // 只返回 id / username / nickname / dept，不泄露手机号邮箱
}

// 保留 /system/user/list —— 管理场景，仍需 system:user
```

**这不构成权限绕过**：返回的是脱敏后的公开信息（同事的姓名和部门），
而真正的操作安全由审批流状态机保障 —— 能不能审批某张单子
取决于 `ap_approval_node` 里该用户是否为当前节点审批人，与能否看到用户列表无关。

**顺带修掉的前端 bug**：

```js
// ❌ 原来：新接口返回 userId，模板却用 u.id → 选项值为 undefined
:key="u.id"  :value="u.id"  :disabled="u.id === userStore.userInfo.userId"

// ✅ 改为
:key="u.userId"  :value="u.userId"  :disabled="u.userId === userStore.userInfo.userId"
```

**以及一个"一次失败就永久失效"的坑**：

```js
// ❌ 原来：只在列表为空时请求，首次 403 后永远不会重试
if (!approverCandidates.value.length) { listEnabledUsers().then(...) }

// ✅ 改为：每次打开弹窗都重新拉，并加错误提示
async function loadApproverCandidates() {
  try { ... } catch (e) { ElMessage.warning('审批人列表加载失败...') }
}
```

## 六 · 五项功能修复详解（2026-10-22）

这五项是同一类问题的集中爆发：**把「数据权限」和「功能权限」搞混了**，
以及**前端筛选控件与后端参数没对齐**。

### 修复 1：工单列表的「全部 / 与我相关」筛选

**现象**：
- zhangsan 选「全部」和「与我相关」结果一样 → 用户以为筛选坏了
- manager/admin 选「与我相关」仍显示全部 → 筛选完全没生效

**根因（两个层次）**：

```
维度一：数据权限（你能看到哪些）—— 后端按角色强制
  管理员/主管：全部
  普通员工：仅「我创建的 + 指派给我的」

维度二：筛选条件（你想看哪些）—— 用户可选
  mine=null（全部） / mine=true（与我相关）
```

二者是**「与」关系**。所以：

- **zhangsan**：数据权限已经限制他只能看自己的，两个选项结果必然相同
  —— 这不是 bug，是数据权限的必然结果
- **manager/admin**：本应不同，但前端单选框**没有 `@change` 事件**，
  只改了 `query.mine` 却没有重新请求数据，必须再点一次「查询」按钮才生效

**修复**：

```java
// 后端：语义化，不再篡改用户的筛选意图
if (!canHandleAll) {
    query.setMine(true);      // 普通员工数据权限强制收敛
    query.setCreatorId(null);
    query.setAssigneeId(null);
}
```

```vue
<!-- 前端：对只能看自己数据的用户，隐藏「全部」选项 -->
<template v-if="canViewAll">
  <el-radio-group v-model="query.mine" @change="handleSearch">
    <el-radio-button :value="undefined">全部</el-radio-button>
    <el-radio-button :value="true">与我相关</el-radio-button>
  </el-radio-group>
</template>
<span v-else class="scope-hint">仅显示与您相关的工单</span>
```

> **产品思维**：给一个只能看自己数据的用户一个「全部」选项，
> 本身就是个误导 —— 点了没变化，用户会以为系统坏了。
> 正确做法是**不给他这个选项**，并明确告诉他「仅显示与您相关的工单」。

### 修复 2：通知中心状态筛选点击无响应

**根因**：`el-radio-group` 只修改 `v-model` 绑定的值，**不会自动重新请求数据**。

```vue
<!-- ❌ 少了 @change，点按钮什么都不发生 -->
<el-radio-group v-model="query.isRead">

<!-- ✅ 加 @change -->
<el-radio-group v-model="query.isRead" @change="handleSearch">
```

> 排查提示：Vue 里凡是「点击某个控件后数据没变化」，
> 先检查**有没有触发重新加载数据**。`v-model` 只负责改值，不负责发请求。

### 修复 3：创建工单时指定处理人

**根因（前后端都缺）**：
- 后端 `TicketDTO` **没有 `assigneeId` 字段** → 就算前端传了也接不住
- 前端创建表单**没有处理人选择项**

**修复**：

```java
// TicketDTO 新增字段
private Long assigneeId;
```

```java
// TicketService.create —— 带权限校验
private Long resolveInitialAssignee(Long requestedId) {
    if (requestedId == null) return null;

    // 权限校验：只有管理岗能指定处理人
    boolean canAssign = SecurityUtils.isAdmin()
            || SecurityUtils.hasPermission("ticket:handle");
    if (!canAssign) {
        log.warn("用户 {} 无权指定处理人，assigneeId={} 已忽略", ...);
        return null;
    }

    // 校验目标用户存在且启用
    SysUser assignee = userMapper.selectById(requestedId);
    if (assignee == null || (assignee.getStatus() != null && assignee.getStatus() != 1)) {
        return null;
    }
    return requestedId;
}
```

> **为什么普通员工不能指定？**
> 指定处理人等于绕过「受理」环节直接甩给别人，破坏了工单状态机的流转规则。
> 普通员工的工单必须先被有受理权限的人认领。

### 修复 4：转派时「新处理人」选不了

**根因**（两个 bug 叠加）：

```js
// ❌ bug 1：字段名错了
users.value = (r.data || []).filter((u) => u.id !== userStore.userInfo.userId)
//                                             ^^^ 接口返回的是 userId，不是 id
//                                             → 选项值是 undefined，选不上

// ❌ bug 2：只请求一次
if (act.code === 'TRANSFER' && !users.value.length) { ... }
//  首次请求失败（如 403）后，users 永远为空且不再重试
```

**修复**：

```js
// ✅ 每次打开都重新加载
if (act.code === 'TRANSFER') { loadTransferCandidates(); }

async function loadTransferCandidates() {
  try {
    const r = await listEnabledUsers()
    users.value = (r.data || [])
      .map((u) => ({ userId: u.userId, nickname: u.nickname, dept: u.dept }))
      .filter((u) => u.userId !== userStore.userInfo.userId)  // 不能转派给自己
  } catch (e) {
    users.value = []
    ElMessage.warning('人员列表加载失败，无法转派，请稍后重试')
  }
}
```

> **教训**：接口改字段名（`id` → `userId`）时，
> 一定要全局搜一遍所有使用点。改后端不改前端，就会出现这种
> "值是 undefined 但不报错"的静默 bug —— 最难查的一类。

### 修复 5：跨角色审批（manager → 员工，员工审批报"没有访问权限"）

**根因**：把**审批权**错误地当成了**角色权限**。

```java
// ❌ 原来
@PreAuthorize("hasAuthority('approval:audit') or hasRole('ADMIN')")
public Result<Void> audit(...) { ... }
```

`approval:audit` 是「审批操作」的角色权限，只有管理员/主管有。
但典型场景是 **manager 发起审批、指定员工审批** ——
此时审批人是普通员工，他不可能有 `approval:audit`，
于是调用 `/approval/audit` 直接被 Spring Security 拦成 403，流程卡死。

**核心认知**：

> **审批权是「数据权限」，不是「功能权限」。**
>
> 能不能审批某张单，取决于**你是不是这单当前节点的审批人**，
> 而不是你的角色是什么。

**修复**：

```java
// ✅ 接口入口放开到 approval:list（所有有审批功能的角色都有）
@PreAuthorize("hasAuthority('approval:list') or hasRole('ADMIN')")
public Result<Void> audit(@Valid @RequestBody ApprovalAuditDTO dto) {
    approvalService.audit(dto);   // ← 真正的安全边界在这里
    return Result.success("审批成功", null);
}
```

业务层的校验本来就正确（`ApprovalService.audit`）：

```java
// 只有节点指定的审批人能审
BusinessException.throwIf(!currentNode.getApproverId().equals(userId),
        ResultCode.APPROVAL_NO_PERMISSION);
```

**为什么不构成越权**：接口放开了，但每个非审批人的调用
都会被业务层拦下并返回 `4003 您不是当前节点的审批人`。
真正的安全边界是**数据归属判断**，不是角色标签。

**验证结果**：

| 场景 | 结果 |
|------|------|
| manager 发起指定 zhangsan 审批 | 成功 |
| zhangsan 待办列表能看到该单 | 成功 |
| zhangsan 审批（无 approval:audit 权限） | 成功 ✅ |
| lisi 越权审批 | `4003 您不是当前节点的审批人` ✅ 正确拒绝 |
